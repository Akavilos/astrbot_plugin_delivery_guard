# 投递哨兵使用指南

适用版本：0.1.3。安装见 [README](../README.md)，数值设置见 [配置参考](配置参考.md)。

## 工作过程

正常会话按间隔检查群禁言，并按配置跟踪协作发送结果。判定不可送达后，哨兵阻止相应模型回复流程，将缺席期间来信保存在自己的收件箱，拦下的出站内容保存在自己的待发队列。

恢复检查确认可发送后，按补发设置处理尚未过期的内容；当前模型请求可获得缺席期的简短背景。并非所有框架或第三方插件的自定义发送路径都能被统一追踪，具体结果应结合适配器日志。

## 首次设置

打开总开关并选择私聊、群聊或全部范围。“跟踪协作发送的结果”用于通过 send_guarded 发送的消息；不接管框架默认发送，私聊故障需要协作发送结果或手动标记。群探测需要机器人在群内，协议端实现相关查询接口。

补发设置中确认有效期、每批条数和间隔。有效期用于避免补发过时内容；每批上限限制一次发送量，不删除超出上限的消息。补发说明文字可以留空。

## 全部指令

| 指令 | 作用 |
|---|---|
| `/哨兵` 或 `/哨兵 status` | 查看当前会话状态、原因、缺席来信与待发数量 |
| `/哨兵 diag` | 查看详细诊断信息 |
| `/哨兵 probe` | 立即探测当前会话，返回结果和状态变化 |
| `/哨兵 flush` | 尝试补发当前会话积压，显示剩余数量 |
| `/哨兵 clear` | 将缺席期收件标记为已处理，不再作为背景注入 |
| `/哨兵 on` | 手动标记当前会话可送达并清除失败计数 |
| `/哨兵 off` | 手动标记当前会话不可送达 |

`on/off` 是当前会话的送达状态标记，不是配置总开关。`clear` 不清空待补发队列。`flush` 是尝试补发，不能保证被协议端拒绝的消息成功送达。

如果本会话已经不可送达，管理指令的返回本身也可能发不出来；此时结合管理日志和插件配置排查。

## 与光谱的配合

哨兵不读取光谱数据库，也不替光谱改写人物和生活。它通过公开事件、协作发送与恢复背景帮助上层识别缺席；未接入协作接口的主动消息不承诺统一跟踪。光谱仍负责自己的发送状态和异常冻结，两者需分别查看。

恢复背景加入当前请求，用于帮助模型接上错过的对话，不会由哨兵写入角色基础人设。与其他改写请求的插件同时使用时，要保留哨兵当前的事件顺序。

## 常见问题

**解除禁言后仍没回复？** 用 `probe` 检查协议端返回值，查看恢复确认次数与轮询间隔。协议端缓存可能延迟状态更新。

**私聊探测没有结果？** 私聊没有对应的送达查询接口。哨兵依赖协作发送结果和有待发内容时的恢复试探，不能主动准确查询所有私聊拒收。

**补发后还有积压？** 检查每批上限、有效期和发送日志。剩余内容仍可能在队列，可根据需要再次 `flush`，不要把剩余数量理解为全部丢失。

**为什么少了旧消息？** 内容可能已过有效期、已成功补发或已按队列策略处理，查看日志与状态。

**一直失败还反复试探？** 检查私聊重试降频是否开启、失败门槛和等待时长，确认协议端错误原因。
